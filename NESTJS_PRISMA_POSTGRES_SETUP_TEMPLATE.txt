6. NestJS Configuration
----------------------
main.ts:
import { NestFactory } from '@nestjs/core';
import { ValidationPipe } from '@nestjs/common';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  app.useGlobalPipes(new ValidationPipe());

  app.enableCors({
    origin: true,
    methods: 'GET,HEAD,PUT,PATCH,POST,DELETE,OPTIONS',
    credentials: true,
  });

  await app.listen(process.env.PORT ?? 3000);
}
bootstrap();

Reusable configuration patterns:
- Bootstraps the root app module.
- Applies a global validation pipe so all DTOs are validated automatically.
- Enables CORS with credential support for browser-based clients.
- Uses process.env.PORT with a fallback of 3000.
- No custom global prefix is configured, which means routes are mounted at the default root path.

9. Authentication Infrastructure
--------------------------------
This project includes a reusable JWT authentication and authorization pattern.

JWT module registration:
JwtModule.registerAsync({
  imports: [ConfigModule],
  useFactory: async (configService: ConfigService) => ({

Reusable authentication guard:
import {
    CanActivate,
    ExecutionContext,
    Injectable,
    UnauthorizedException,
} from '@nestjs/common';
import { JwtService } from '@nestjs/jwt';
import { Request } from 'express';
import { Reflector } from '@nestjs/core';
import { IS_PUBLIC_KEY } from '../decorators/public.decorator';

@Injectable()
export class AuthGuard implements CanActivate {
    constructor(private readonly jwtService: JwtService, private readonly reflector: Reflector) { }

    async canActivate(context: ExecutionContext): Promise<boolean> {
        const isPublic = this.reflector.getAllAndOverride<boolean>(IS_PUBLIC_KEY, [
            context.getHandler(),
            context.getClass(),
        ]);
        if (isPublic) {
            return true;
        }

        const request = context.switchToHttp().getRequest();
        const token = this.extractTokenFromHeader(request);
        if (!token) {
            throw new UnauthorizedException();
        }
        try {
            const payload = await this.jwtService.verifyAsync(token);
            request['user'] = payload;
        } catch {
            throw new UnauthorizedException();
        }
        return true;
    }

    private extractTokenFromHeader(request: Request): string | undefined {
        const [type, token] = request.headers.authorization?.split(' ') ?? [];
        return type === 'Bearer' ? token : undefined;
    }
}

Public decorator:
import { SetMetadata } from '@nestjs/common';

export const IS_PUBLIC_KEY = 'isPublic';
export const Public = () => SetMetadata(IS_PUBLIC_KEY, true);

Role-based guard:
import { Injectable, CanActivate, ExecutionContext, ForbiddenException } from '@nestjs/common';
import { Reflector } from '@nestjs/core';
import { ROLES_KEY } from '../decorators/roles.decorator';

@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private reflector: Reflector) {}

  canActivate(context: ExecutionContext): boolean {
    const requiredRoles = this.reflector.getAllAndOverride<string[]>(ROLES_KEY, [
      context.getHandler(),
      context.getClass(),
    ]);
    if (!requiredRoles) {
      return true;
    }
    const { user } = context.switchToHttp().getRequest();
    if (!user || !user.role) {
      throw new ForbiddenException('You do not have permission (no role found)');
    }

    if (requiredRoles.includes(user.role)) {
      return true;
    }

    throw new ForbiddenException('You do not have the required roles to access this resource');
  }
}

Roles decorator:
import { SetMetadata } from '@nestjs/common';
export const ROLES_KEY = 'roles';
export const Roles = (...roles: string[]) => SetMetadata(ROLES_KEY, roles);

Generic auth service pattern:
import { Injectable, UnauthorizedException } from '@nestjs/common';
import { JwtService } from '@nestjs/jwt';
import { PrismaService } from '../prisma/prisma.service';

@Injectable()
export class AuthService {
  constructor(
    private readonly prisma: PrismaService,
    private readonly jwtService: JwtService,
  ) {}

  async login(loginDto: any) {
    const credential = await this.prisma.someEntity.findUnique({
      where: { identifier: loginDto.identifier },
    });

    if (!credential) {
      throw new UnauthorizedException('Invalid credentials');
    }

    const payload = { sub: credential.id, username: credential.username, role: credential.role };
    return {
      access_token: await this.jwtService.signAsync(payload),
      user: {
        id: credential.id,
        username: credential.username,
        role: credential.role,
      },
    };
  }
}

Reusable ideas:
- Use a custom guard to verify bearer tokens globally.
- Use @Public() to bypass auth for public endpoints.
- Use Roles and a permission guard to enforce claims.
- Attach authenticated payload to request.user.
- Keep JWT secrets in environment variables.

11. Error Handling
------------------
This project uses NestJS standard HTTP exceptions and a global validation pipe for error handling.

Examples of reusable exceptions used in services:
- UnauthorizedException for invalid credentials or expired tokens
- ForbiddenException for insufficient permissions
- BadRequestException for invalid or duplicate payloads
- NotFoundException for missing records

Validation errors are handled automatically by the global ValidationPipe (with class-validator).

Global validation pipe:
app.useGlobalPipes(new ValidationPipe());

This ensures DTO validation errors become structured NestJS HTTP validation responses instead of ad hoc manual checks.

Prisma-related errors are not globally normalized in this project; the typical architecture is to catch Prisma exceptions in service code and map them into NestJS HTTP exceptions as needed.

Recommended generic error-handling pattern for new projects:
- Validate DTOs centrally with ValidationPipe.
- Throw standard NestJS exceptions from services.
- Keep auth errors as UnauthorizedException or ForbiddenException.
- For Prisma errors, catch PrismaClientKnownRequestError and map to BadRequestException or NotFoundException as appropriate.

15. Important Problems / Gotchas
--------------------------------
These are the technical issues and compatibility patterns that matter when reproducing the same foundation:

1. Prisma adapter and generated client path
- The project imports PrismaClient from generated/prisma/client.js instead of the default generated location.
- If the output path changes or the client is regenerated in a different location, imports will fail.
- Reproduction must preserve the generated output configuration.

2. Prisma generate must run before build
- The build script explicitly runs prisma generate before nest build.
- This avoids stale generated client issues after schema changes.

3. NodeNext TypeScript configuration is required for this Prisma pattern
- The project uses module and moduleResolution set to nodenext.
- This matters for modern Node and Prisma ESM/CJS compatibility.

4. DATABASE_URL must be present before startup
- PrismaService creates a PrismaPg adapter using process.env.DATABASE_URL.
- Missing or invalid database URLs will break startup.

5. JWT secret must exist
- The app sets the JWT secret from JWT_SECRET with a fallback only for local development.
- Production should never rely on default secrets.

6. Global guards can block all routes if not configured correctly
- APP_GUARD is used to register auth and role checks globally.
- Public endpoints must use the @Public() decorator.
- If a new route is unauthenticated but not marked public, it will be blocked.

7. CORS must be enabled when browser clients are used
- The project enables CORS with credentials and origin true.
- This is a common requirement for frontend-backend separation.

8. ValidationPipe should be global
- Without a global validation pipe, DTO validation will not run automatically.
- This is a core reusable pattern for clean request validation.

9. Prisma lifecycle hooks are important
- Prisma connects in onModuleInit and disconnects in onModuleDestroy.
- This is the clean NestJS lifecycle pattern for database clients.

10. Production start path should match compiled output
- The project starts with node dist/src/main.js.
- This is a common gotcha when moving from src-based NestJS dev mode to built production mode.
