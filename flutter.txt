FLUTTER FRONTEND DOCUMENTATION
Category + Subcategory + Brand

Base URL
- http://localhost:3000

This document is for Flutter app usage.
It covers the GET endpoints that are relevant for the app flow, and explains the navigation pattern we plan to use.

AUTH + ROLE RULES
The app user role is:
- CLIENT

This means the Flutter app should authenticate as a user with role CLIENT when using the storefront flow.

The system roles in the Prisma model are:
- CLIENT
- ADMIN
- DELIVERY
- ORDERS_STAFF
- ACCOUNTS_STAFF
- SUPPORT

Important auth rules:
- Public category / subcategory / brand endpoints do not require an auth token.
- If the app later adds protected routes, the token must be sent as:
  Authorization: Bearer <token>
- The app should expect 401 Unauthorized when the token is missing or invalid.
- The app should expect 403 Forbidden when the user does not have the required role.

IMPORTANT: RESPONSE SHAPE
All successful responses are wrapped by the global interceptor.
So every success response looks like:
{
  "message": "Success",
  "data": { ...actual payload... }
}

Examples:
{
  "message": "Success",
  "data": [
    {
      "id": 1,
      "name": "Electronics"
    }
  ]
}

Errors still use the Nest default format:
{
  "message": "Something went wrong",
  "error": "Bad Request",
  "statusCode": 400
}

IMPORTANT NOTE FOR FLUTTER FLOW
There is no dedicated GET endpoint like:
- /brand?subcategoryId=11
- /subcategory?categoryId=1

So for the app flow today, use this pattern:

Flow 1: Home page
- Call GET /category
- Show category cards on the home screen

Flow 2: Category selected
- User taps a category, for example category id = 1
- Use GET /category/1
- Read category.subcategories
- Show subcategory cards

Flow 3: Subcategory selected
- User taps subcategory id = 11
- Call GET /brand
- Filter the list in Flutter by checking each brand.brandSubCategories
- Keep only brands where any subCategory.id equals 11
- Show the filtered brands list

Flow 4: End of current phase
- At this point, the app has reached the brand screen for the chosen subcategory.
- This is the final flow for the current phase.
- When the product module is ready, we will continue the flow:
  - selected subcategory + selected brand
  - then call product endpoints to load products filtered for that subcategory and brand

Example filter logic in Flutter (conceptually):
final selectedSubCategoryId = 11;

final filteredBrands = allBrands.where((brand) {
  return brand.brandSubCategories.any(
    (item) => item.subCategory?.id == selectedSubCategoryId,
  );
}).toList();

RECOMMENDED APP FLOW
1. Home screen
   - GET /category
   - display category cards

2. Category detail screen
   - GET /category/:id
   - display subcategories

3. Subcategory screen
   - use selected subcategory id
   - GET /brand
   - filter by matching subCategory.id
   - display brands

4. Brand screen
   - when ready, later fetch products for selected brand + selected subcategory

CURRENTLY IMPLEMENTED FLUTTER DATA FLOW
- Category -> subcategory is already supported by the category detail response
- Brand relationship is supported through brand.brandSubCategories
- Product list is not implemented yet, so we stop after brand selection for now

SUMMARY
For Flutter right now, use these routes:
- GET /category
- GET /category/:id
- GET /sub-category
- GET /sub-category/:id
- GET /brand
- GET /brand/:id

And use this navigation flow:
Home -> Category -> Subcategory -> Brands

This is the current app flow we need before the product module is ready.
